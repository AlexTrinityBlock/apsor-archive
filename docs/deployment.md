## Quick start

### Docker Compose (production)

The production stack is **Cloudflare Tunnel → Caddy → API + ingestion worker**,
with PostgreSQL, Valkey, RabbitMQ, and (by default) a bundled RustFS object
store on the private Compose network. It publishes no host port.

Run the setup wizard instead of writing environment variables by hand:

```bash
./start.sh setup        # or: make setup
mkdir -p data && sudo chown -R 10001:10001 data
docker compose up -d --build
```

The wizard asks for the public hostname, the storage backend (bundled
**RustFS** by default, or Cloudflare R2, or any S3-compatible endpoint, or local
disk), the session lifetime, an optional DeepSeek key, and the Cloudflare
Tunnel token. It writes the non-secret `.env`, generates the RustFS and
RabbitMQ credentials, stores pasted keys in `.secrets/*.env` and `secrets/*.txt`
without echoing them, keeps any existing file unless you confirm an overwrite,
and prints the `sudo chgrp` commands the containers need to read the secret
files. `./setup.sh --defaults` runs the same flow non-interactively (production
with RustFS); add `--dev` for a development `.env`.

Point the Cloudflare Tunnel public hostname at **HTTP `caddy:80`**, then open
`https://$APSOR_PUBLIC_HOST`. Put `APSOR_PUBLIC_HOST` in `.env` so restarts keep
the host matcher. The first visit asks you to create the root account. The root
can then create normal accounts from **Accounts**; each new account receives a
one-time temporary password and must change it at first sign-in. PostgreSQL
uses a named volume; local original bytes and the generated secret key live
under the host's `./data` directory. Original file bytes go to the backend the
wizard selected; see [Object storage](#object-storage-rustfs-r2-s3-or-local).

> Note: `./data` is bind-mounted into the container and the container process
> runs as uid `10001`. Create the directory and fix its owner before the first
> boot, otherwise uploads and original-byte writes fail. If the host user is
> already uid `10001`, the `sudo chown` can be skipped.

The `postgres-data` volume is pinned to an explicit physical name:
`apsor-archive_postgres-data` for `docker-compose.yml` and
`apsor-archive-dev_postgres-data` for `docker-compose.dev.yml`, so a Compose
project rename cannot orphan the database. A stack created before this rename
used a different physical volume name, so copy that volume's contents into the
new one (or keep the old name in the local Compose file) before starting.
Otherwise PostgreSQL initialises an empty database.

The Docker build compiles the frontend from `frontend/` in a Bun stage, so
`docker compose up --build` picks up a frontend change without a manual build.
Run `cd frontend && bun run build` only when you want a local preview.

To enable AI answers and AI summaries:

```bash
mkdir -p .secrets
printf 'APSOR_DEEPSEEK_API_KEY=sk-your-key\n' > .secrets/deepseek.env
chmod 755 .secrets
sudo chgrp 10001 .secrets/deepseek.env
chmod 640 .secrets/deepseek.env
docker compose up -d --build
```

The Compose file mounts `.secrets/` read-only. The app reads the env file itself,
so the key never becomes a container environment variable and never appears in
`docker compose config`. The API container runs as uid `10001`, so the file must
be readable by that uid: group `10001` with mode `640`, or `644` on a
single-user host. The key is gitignored and is never returned by the API.
Without it, summaries fall back to a deterministic extractive form, image
uploads use the filename caption, and agent messages return
`503 agent_not_configured`.

### Object storage (RustFS, R2, S3, or local)

`APSOR_STORAGE_BACKEND` chooses the default for new original bytes. The setup
wizard sets it; every option uses the same S3-compatible adapter except `local`.

| Value | Where bytes go | Credentials |
|---|---|---|
| `rustfs` | The bundled RustFS service (`COMPOSE_PROFILES=rustfs` starts it). Default for new installs. | Generated by the wizard into `.secrets/s3.env` and `secrets/rustfs_*_key.txt` |
| `r2` | A private Cloudflare R2 bucket | `.secrets/r2.env` |
| `s3` | Any S3-compatible endpoint (AWS S3, MinIO, another RustFS) | `.secrets/s3.env` |
| `local` | `APSOR_DATA_DIR`; the default for development and tests | none |
| `auto` | R2 when `.secrets/r2.env` is complete, else S3, else local | — |

`rustfs` is an alias of `s3`. When `APSOR_STORAGE_BACKEND` is unset, the
production Compose file uses `auto`, so an existing R2 deployment keeps writing
to R2 without an `.env` change. Each row records the backend that holds its
bytes (`local`, `r2`, or `s3`), and every backend whose settings are complete
stays readable, so a staged migration can serve a mixed archive.

Non-secret settings live in `.env`:

- R2: `APSOR_R2_ENDPOINT_URL` (`https://<account-id>.r2.cloudflarestorage.com`,
  no default), `APSOR_R2_BUCKET` (`apsor-archive`), `APSOR_R2_REGION` (`auto`),
  `APSOR_R2_PREFIX`.
- S3 / RustFS: `APSOR_S3_ENDPOINT_URL` (Compose default `http://rustfs:9000`),
  `APSOR_S3_BUCKET` (`apsor-archive`), `APSOR_S3_REGION` (`us-east-1`),
  `APSOR_S3_PREFIX`, `APSOR_S3_ADDRESSING_STYLE` (`path` or `virtual`), and
  `APSOR_S3_CREATE_BUCKET` (create a missing bucket on the first write; the
  bundled RustFS needs it).

Access keys never go in `.env` or container environment variables. Compose
mounts `.secrets/` read-only and the app reads `r2.env` / `s3.env` itself; the
RustFS container reads its pair as Docker secrets. All of them run as uid
`10001`, so the files need group `10001` with mode `640` (the wizard prints the
`sudo chgrp` command). Buckets stay private: no presigned URLs, no public
access, and no lifecycle expiry on `files/`. `data/.secret_key` is the Fernet
master key and remains local; back it up separately from PostgreSQL. Back up
the `apsor-archive_rustfs-data` volume (or the external bucket) with the
database as one backup set.

To move an existing archive from local disk to R2, stop the API and worker and
run the storage CLI from `backend/`:

```bash
uv run python -m script.migrate_storage_to_r2 --dry-run
uv run python -m script.migrate_storage_to_r2 --copy
uv run python -m script.migrate_storage_to_r2 --verify
# only after a verified backup and rollback window
uv run python -m script.migrate_storage_to_r2 --delete-local
```

`--copy` uploads and verifies size and SHA-256, then marks the matching `file`
and retryable `file_ingest_job` rows as `storage_backend='r2'`. Keep the
PostgreSQL dump, the data-directory backup, and the R2 bucket contents together
as one backup set. Back up the bucket with versioning or an object-sync job;
soft-deleted files keep their objects.

### Cloudflare Tunnel

The production Compose stack already contains `cloudflared`, Caddy, and the
API. In the Cloudflare dashboard, add one public hostname:

- **Service type**: `HTTP`
- **URL**: `caddy:80`

`cloudflared` makes outbound connections, so no router port forwarding is
needed. Caddy serves only the host named by `APSOR_PUBLIC_HOST` and answers
`404` for every other host; do not add a second public hostname to the tunnel
ingress. See `secrets/README.md` for token permissions and
[`docs/cloudflare-tunnel.md`](../docs/cloudflare-tunnel.md) for the complete
deployment, backup, security, and troubleshooting guide.

### Home network (no tunnel)

To try Apsor Archive on your own computer or home network, skip the tunnel and
let Caddy publish port 8080:

```bash
./start.sh setup                     # choose "production"; leave the tunnel token empty
# in .env, set APSOR_PUBLIC_HOST to the name you will type in the browser,
# for example: APSOR_PUBLIC_HOST=localhost
docker compose -f docker-compose.yml -f docker-compose.local.yml up -d --build
```

Open `http://localhost:8080` (or `http://<that name>:8080`). The override
(`docker-compose.local.yml`) switches the tunnel connector off and lets the
session cookie work over plain HTTP. Set `APSOR_LOCAL_PORT` in `.env` to use a
different port. Use the Cloudflare Tunnel for anything reachable from the
internet.

### Docker Swarm

`docker-stack.yml` runs the same services on a single-node Swarm. Swarm does not
build images and does not read `.env`, so build with Compose first and load
`.env` into the shell:

```bash
./start.sh setup                     # once: writes .env and the secret files
docker compose build                 # tags apsor-archive-api, -worker and -caddy
docker swarm init                    # once, if this machine is not a manager yet
set -a; . ./.env; set +a
docker stack deploy -c docker-stack.yml apsor
docker stack services apsor          # watch the services come up
```

Every service is pinned to the manager node because the archive data, the
`.secrets/` folder and the broker config are bind mounts on that machine.
`depends_on` is ignored by Swarm, so the API and worker simply restart until
PostgreSQL is ready (usually within a minute). RustFS is always part of the
stack; if you store files in Cloudflare R2 or another S3 service, run
`docker service scale apsor_rustfs=0`. To update, pull the new code, run
`docker compose build` again, then repeat the `docker stack deploy` line.
