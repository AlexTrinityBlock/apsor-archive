# Agent Module — Agent Guide

The agent slice owns the persistent archive agent: an append-only transcript, durable run state, deterministic context projection, validated tools, SSE streaming, human approval, compaction, retry, forking, runtime settings, system prompts, and saved questions.

## Purpose

Keep one conversation resumable and auditable across model steps and process restarts. Provider payloads and UI payloads are separate; every turn is a durable operation, not an in-memory chat array.

## Architecture

- `model/agent_model.py` defines `agent_conversation`, immutable `agent_entry`, operational `agent_run`, durable `agent_approval`, and temporary `agent_chat_attachment`. `agent_config` (`model/agent_config_model.py`) stores the singleton runtime limits; `saved_question` and `system_prompt_section` live in their own modules.
- Pasted chat images live under `users/{user_id}/chat-temp/` in object storage and are tracked by `agent_chat_attachment`. A user entry stores only attachment ids and display metadata in `data`; at provider-call time the attachment service loads the bytes and materializes OpenAI-compatible `image_url` parts. Deleting a temporary image is a soft delete of the row plus object deletion, so history stays append-only and the UI can show a placeholder.
- Conversation memory is a flat index over `pi.user` and `pi.assistant` text. `AgentHistoryIndexer` discovers entry ids across owners with a maintenance session that returns ids only, then reads each owner's entries and writes 256-character windows (32-character overlap, stride 224) through the knowledge-side `HistoryChunkStore` into the shared `chunk` table as `source_kind='history'`. It backfills from entry id 0, skips already-indexed entries, ignores empty tool-call-only assistant turns, and marks a soft-deleted conversation's windows non-current. `search_knowledge` returns the top 15 history windows after cosine recall, BM25 scoring, and RRF rerank; each is rendered as `<history_message id="...">`. The read-only `history_message` tool expands one entry id into the full immutable message and bounded neighbours. Never index tool results, page context, system prompts, or chat-image bytes as conversation text.
- A staged image is discarded when the composer removes it or leaves the chat. The browser sends a `client_token` on upload; it makes a retried upload idempotent and lets `POST /api/v1/agent/attachments/cancel` discard a row when the XHR was aborted before its response arrived. Cancel is a conditional soft delete (`entry_id IS NULL`), so it never removes an image a message has claimed, and repeating it is safe. The cleanup service is the final backstop: staged images expire after `chat_attachment_staged_ttl_hours` (default 1), swept every `chat_attachment_cleanup_interval_seconds` (default 900) by the worker (or the API when it owns the ingestion loop). Both values live in the `agent_config` singleton and are edited from the root Agent runtime settings; they are not environment variables. Images sent with a message are promoted from `chat-temp/` to `chat-images/` before the claim and are never swept. Cleanup discovers ids with a maintenance session, then claims each row in its owner's RLS context with a conditional update before deleting the object.
- Entries use kinds `pi.system`, `pi.user`, `pi.assistant`, `pi.tool-result`, `pi.page-context`, `pi.compaction`, `pi.reset`, and `ui.notice`. `model` is exactly the provider-facing messages; `data` is UI/telemetry and is never sent to the provider.
- The transcript is append-only. Corrections are new boundary entries, context `edits`, or `head_entry_id` changes on a new entry, never updates or deletes of `agent_entry`. One transaction reserves one `agent_commit_seq`, shared by all entries written together.
- `AgentRepository` owns its own short sessions and row locks. This lets an SSE response outlive a request session. Runs move through `running`, `waiting`, `completed`, `failed`, and `cancelled`; only one `running` or `waiting` run may exist per conversation, and request ids are idempotent.
- `begin_message` locks the conversation, rejects an active run, resolves the request id, appends any auto-compaction, an optional page-context snapshot, and the user entry in one transaction, then creates the running run.
- `begin_retry` creates a new run for the latest `failed` or `cancelled` user entry. It does not duplicate the user message; a completed run is not retryable.
- Conversation detail returns the **newest** entry page so a chat opens at the tail. `previous_before_id` walks backward into older entries; `/entries` keeps `after_id` for forward reads and adds `before_id` for the same backward walk. The full transcript stays append-only; pagination must never hide the newest plot, image, or compaction boundary.
- `AgentRuntimeConfig` is an immutable per-request snapshot. It is loaded in a short-lived session before the stream starts; an active stream keeps its snapshot while later runs see new settings. It carries the compaction template/output cap, `model_escalation_enabled`, and `agent_max_output_tokens`; the account's context-window and compaction-threshold overrides are applied over it. Primary endpoint/model/effort come from the account assignment, not `AiRuntime.chat_config`.
- `domain/context_domain.py` deterministically projects entries into a provider request: newest `head_entry_id` selects the active segment; edits are applied; the frozen system/tool snapshot is retained; tool results follow their assistant call; missing results are synthesized; orphan results and failed assistant attempts are excluded.
- Current-time metadata is appended after the user text by the context projection. Page-context snapshots are append-only and deduped by key within the active segment. Compaction/reset boundaries start a new active segment and KV-cache lineage without rewriting earlier rows.
- `AgentService._run_loop` is bounded by the snapshot's step, tool-call, parallel, and per-result character limits. Parallel eligible calls run through `asyncio.gather` with a semaphore; persistence and emitted `tool_end` events still follow assistant call order.
- `service/tool_registry.py` validates arguments with Pydantic, dispatches the thirteen catalog tools (`search_knowledge`, `read_file`, `read_timeline`, `read_path`, `read_memory`, `history_message`, `save_memory`, `present_resource`, `calculate`, `render_plot`, `web_search`, `web_fetch`, and the read-only `companion_action` gesture), clips each provider-facing result, and turns expected failures into structured `pi.tool-result` errors. A tool failure must not become an HTTP 500 or crash the turn.
- Each tool call gets a separate database session through `_ToolServiceScope`. The tool layer sees knowledge/web-research protocols assembled in `dependencies.py`, not a long-lived request session.
- Companion persona and lore come from the `companion` slice through `dependencies.py` only. `create_conversation` freezes the active persona as the last `companion_persona` section and `data.companion = {ref, name, locale}`; the section's rules (persona rules and the equal-address rule) come from the companion config templates, so the agent appends no story wording of its own. The companion's own memories enter a run through **one** path, `CompanionContextContributorProtocol`: `begin_message` builds one `ContextSignal` per input site (the user's words, the page-context text of a document preview, attachment display names — never bytes) and stores the rendered block on the user entry (`data.companion_context`, `data.companion_context_ids`), which the context builder appends after `time_context` (`domain/companion_context_domain.py`, `USER_SUFFIX_KEYS`; the legacy `data.story_moment` key is still read). `AgentToolRegistry.execute` asks the same contributor once after every successful `read_file`, `read_memory`, `read_timeline`, `present_resource`, or `web_fetch` result and appends one `<librarian_memories>` block inside a reserved share of the result budget (`data.lore`, never a source or citation). A per-run `CompanionTurnContext` carries offered ids so the per-run cap holds across sites and nothing repeats. Contributor errors are logged and ignored. `search_knowledge` searches only the person's archive and never carries lore. Nothing is locked: every memory carries a `weight` (everyday, past, heart) and blocks carry relationship facts (`days_known`, `conversations_together`, `first_met`); the librarian decides what to share (seeded `memory_agency` template). The read-only `recall_my_memories` tool (withheld when the conversation froze no companion) returns her lore and published life stories (`scope=story`, told with source `recall`) and past assistant replies by any librarian (`scope=said`, labeled `said_by`, her own first). `AgentRepository.append_assistant` stamps every reply with `data.speaker = {ref, name}` from the frozen companion; `AgentEntrySchema.speaker` exposes it, and history windows and `history_message` show `role` and `speaker`. `AgentService._complete_run` reports completed runs to `CompanionRunObserverProtocol` best-effort (run and conversation counts, first met).
- Tool results carry UI-only `data` (bounded excerpts, viewer descriptors, durations, arguments). Provider content is XML wrapped in a `<tool_result>` envelope; never feed UI data to the model.
- `save_memory` is the only confirmation-required tool. With `save_memory_requires_approval` on, validated arguments create durable approval rows, the run becomes `waiting`, and no tool result exists until an explicit approve/reject. With it off, only the backend authorizes execution. Model-supplied `user_confirmed` never authorizes a write.
- Approval resolution claims the row once, requires earliest-pending order, appends the real result (or `memory_rejected`), and resumes the stored loop snapshot. Startup fails stale `running` runs as `interrupted` and waiting runs without a pending approval as `approval_orphaned`.
- Messages and retry endpoints return `text/event-stream` unless `Accept: application/json` is sent. Event names are `run_start`, `message_start`, `message_delta`, `reasoning_delta`, `message_end`, `tool_start`, `tool_end`, `approval_required`, `run_end`, and `error`. Assistant deltas are transport-only; the assistant entry is persisted at `message_end`. `reasoning_delta` carries provider thinking before the corresponding text/tool events and is never merged into `message_delta`. SSE headers disable buffering and cache transforms.
- Conversation creation freezes one `pi.system` entry containing ordered prompt sections, the signed-in account's profile, the complete tool snapshot, and prompt/tools versions. Editing prompt rows affects only new conversations.
- Compaction is deterministic and never calls the provider: it builds a bounded `<compaction>` message with a self head, rendered from the root-editable `compaction_prompt` (which must contain `{max_output_tokens}`) under `compaction_max_output_tokens`. It runs before a new user turn and again before each provider step when tool/page growth pushes the estimated context over the threshold. New summaries merge consecutive identical tool results into one counted line, carry a bounded concrete primary argument per tool line, omit empty assistant lines, and add one `Thinking: <first 200 characters>` line only when an assistant entry has non-empty `data.reasoning`. That line is a bounded model-reasoning trace, not a verified fact, and the full reasoning stream never enters the summary. A provider context-window rejection triggers one compaction retry inside the same run. The local overflow ladder never raises a context error: forced compaction at 60% of the budget, page-context drop, tool-result clipping at 8,000/2,000/500 characters, then outbound-copy truncation with one `ui.notice`; the stored transcript is unchanged. With `model_escalation_enabled`, one same-endpoint escalation to the next catalog tier is allowed per run on the documented triggers, never on 5xx/timeout/401/403/quota. Clear appends a self-headed `pi.reset`; both boundaries preserve the full transcript. Fork copies entries through an inclusive cutoff, remaps head/edits, and copies no runs or approvals.
- Saved questions are a separate Q&A surface. CRUD does not require a configured chat provider; `ask` creates a conversation, runs one turn, and writes the latest answer, citations, status, and error back to the same row.

## Key files

- `service/agent_service.py` — turn loop, streaming events, compaction, retry, approvals, fork orchestration.
- `repository/agent_repository.py` — append-only transactions, locks, commit sequence, run recovery.
- `domain/context_domain.py` — entry-to-provider context replay.
- `domain/compaction_domain.py` — token estimate and deterministic summary boundaries.
- `domain/tool_catalog.py` / `domain/tool_args.py` — frozen tool schemas and validators.
- `service/tool_registry.py` — dispatch, error normalization, result clipping, UI previews.
- `service/chat_attachment_service.py` — image validation/re-encoding, temporary storage, manager CRUD, and provider image materialization.
- `service/chat_attachment_cleanup.py` — staged-only expiry sweep with a database-backed config provider and an owner-scoped conditional claim.
- `service/history_indexer.py` — cursor-based backfill and ongoing indexing of conversation windows, including deleted-conversation retirement.
- `service/history_message_service.py` / `repository/history_repository.py` — owner-scoped reads for `history_message` and the indexer.
- `domain/history_domain.py` — fixed 256/32 windowing and message-text extraction.
- `router/conversation_router.py` / `router/approval_router.py` / `router/chat_attachment_router.py` — SSE/JSON transports and temporary-image management.
- `domain/system_entry_domain.py` — seed prompt sections and the frozen `pi.system` entry builder (`build_system_data` / `build_system_model`).
- `service/system_prompt_service.py` — root CRUD over `system_prompt_section`.
- `domain/time_context_domain.py` — the trusted `<current_time>` block appended to user entries.
- `domain/agent_status_domain.py` — the trailing `<agent_status>` block.
- `dependencies.py` — composition root, config snapshot, short-lived tool sessions, test seams.
- `test/fake_chat_generator.py` — deterministic test fake; this package contains no collected tests.

## Agent status block

`domain/agent_status_domain.py` renders the one trailing status message each provider call receives; `_provider_messages` places it.

- The chat loop appends one `<agent_status>` message as the **final** `system` message of every provider call: `[frozen system] + context.messages + [agent_status]`.
- It contains the runtime limits the model may need (`max_expression_chars`, `max_page_context_chars`, `max_tool_result_chars`, and `output_limit_tokens` unless the cap is disabled), plus an optional `<retry_notice>`, plus five context-budget values:
  - `context_used` — conservative estimated tokens of the complete ordered request for this call: the frozen system message, the tool snapshot, every replayed context message in order, and this trailing status block itself. It is `max(character estimate, reported prompt tokens)` for the current segment, not a provider-exact count.
  - `context_limit` — the effective input budget (`context_window_tokens` after the account override is applied).
  - `context_remaining` — `max(0, context_limit - context_used)`.
  - `compaction_at` — the effective `compaction_threshold_tokens`.
  - `compaction_in` — `max(0, compaction_at - context_used)`.
- `_agent_status_message` estimates with `estimate_provider_context_tokens`, the same script-weighted ratio as the budget ladder, and the provider-reported prompt floor. It assumes the `_provider_messages` order above and never calls a provider or tokenizer. Because the block renders its own estimate, a bounded fixed-point loop (at most three render/estimate passes) converges the total, and the final block carries the final estimate. Inline image data URLs are stripped so raw base64 bytes are not counted.
- If the estimate is at or above `context_limit`, the block reports `context_remaining="0"` and `compaction_in="0"`; the local budget never raises a context-limit error.
- Attributes are rendered in sorted order; identical inputs must produce byte-identical output.
- The block is provider-only: it is never persisted and never enters `cache_prefix_hash`, and the frozen prompt/tool prefix must not change because of it.
- Only these five bounded context-budget numbers may be added as mutable telemetry. User/account/conversation/run ids, titles, archive content, paths, provider keys or base URLs, usage counters, and tool names remain forbidden; the minimal shape is intentional.

## Context accounting

- `estimate_provider_context_tokens` and `estimate_context_tokens` stay deterministic and offline. Their input estimate is script-weighted: non-CJK characters keep the model catalog's `chars_per_token` ratio unchanged, while CJK characters (Han, kana, Hangul, CJK punctuation, and fullwidth blocks) are charged at `1.6` characters per token. The weight is applied to the serialized request, so a pure-ASCII request produces exactly the previous estimate and a Chinese request is materially more conservative. Only the input estimate changes; `render_compaction_prompt`, `_char_budget`, and every output-token character budget keep the catalog ratio.
- The configured `context_window_tokens` is never lowered and the account's setting is never rewritten to compensate for an estimate. The estimate becomes accurate enough for the configured budget to be meaningful.
- `AgentService` remembers the largest successful `usage["prompt_tokens"]` reported by the provider for the current context segment. Every budget decision uses `max(character estimate, reported prompt tokens)`. A compaction that starts a new context segment (persisted compaction, forced overflow compaction, or the start of a resumed loop) clears the floor because the old prompt size no longer describes the new request.
- `_enforce_context_budget` and `_agent_status_message` both use that floor. After a provider reports an overshoot, the next step runs the existing ladder (forced compaction, page-context drop, tool-result clipping, outbound truncation) instead of repeating the same oversized prompt; there is no new hard error. A single call can still overshoot only when the provider ignores the configured local budget, never because the next step ignored a reported prompt size.
- `context_used` is therefore conservative, not a provider-exact token count. It must never be described as the provider's authoritative usage; the authoritative figure is the `prompt_tokens` in entry `data.usage`.

## Reasoning capture

- `ChatResult.reasoning` carries provider reasoning/thinking text when the provider returns it. DeepSeek exposes `reasoning_content` in both non-streaming messages and streamed deltas; Anthropic exposes returned `thinking` content blocks and `thinking_delta` events. Request semantics do not change: no new thinking mode is enabled, and an omitted reasoning field stays empty. Reasoning is never synthesized.
- `complete_chat` accepts an optional `on_reasoning_delta` callback beside `on_text_delta`. The agent loop queues reasoning separately and emits the transport-only `reasoning_delta` SSE event with `{"entry_id": null, "delta": "..."}` before the corresponding text or tool events. `message_delta` remains text-only, and a reasoning delta counts as visible output for the automatic-retry guard so a retry cannot duplicate it.
- Reasoning is persisted only in assistant entry `data`: `reasoning` (bounded by `MAX_ASSISTANT_REASONING_CHARS`, 20,000), `reasoning_chars` (original length), `reasoning_truncated`, and `reasoning_tokens` when the provider usage reports it. The provider-facing `model` message stays exactly the visible text plus tool calls, and reasoning never enters the frozen system prefix, `cache_prefix_hash`, the tool XML, or a provider request. Never log the reasoning text.
- Reasoning is display-only honesty telemetry. A persisted step renders a collapsed plain-text `Thinking` block, a live step may show it open, and the assistant usage row shows `reasoning_tokens` when positive. A provider that returns no reasoning produces no event, no data keys, and no placeholder.

## Conventions

- Never update or delete an entry to fix history. Append a new entry, boundary, edit, or run state change. Preserve `commit_seq` grouping.
- Keep provider `model` and UI `data` separate. If the model should see new content, put it in `model`; if only the inspector needs it, put it in `data`. Temporary chat images are the deliberate exception: the entry keeps ids/metadata in `data` and the attachment service injects bytes into the provider payload at call time.
- Chat images must be verified and re-encoded server-side; never trust the client MIME type or extension. The only accepted outputs are PNG, JPEG, and WebP. Never log storage keys, file names, image bytes, or data URLs. The `(user_id, client_token)` constraint is the idempotency guard; an upload retry returns the existing staged row, and cancel must never touch a row with `entry_id` set.
- The lifetime sweep must claim a due row with a conditional update before deleting its object. Never delete a staged object from a stale read; a message may be claiming the same row concurrently.
- Do not hold the request database session in the loop, tool execution, or stream generator. Open short sessions for appends and tool calls.
- Preserve SSE event names, payload fields, and ordering. Add new event fields compatibly; do not persist incremental assistant deltas.
- Add tools only with a validated argument model, catalog entry, registry dispatcher, and prompt/tools version decision. Bump `PROMPT_VERSION` or `TOOLS_VERSION` when the frozen prefix changes; existing conversations must stay frozen. `history_message` is read-only and must not become a write or approval path.
- Keep history windows deterministic: 256 characters, 32-character overlap, stride 224, raw text only. The XML `<history_message id="...">` envelope is applied when rendering a search hit or tool result, never stored in `chunk.content`. A history search hit's id is the immutable `agent_entry` id; never invent or remap it.
- `web_fetch` is page-based: the model sees only `url` and `page`, and the service returns one server-defined page of up to 12,000 characters packed at whole-line boundaries. `page`/`total_pages`/`page_chars`/`total_chars`/`has_more`/`next_page` and the continuation footer are part of the frozen tool contract. The legacy `offset`/`limit`/`max_chars` arguments remain accepted but are hidden from the model-facing schema (`SkipJsonSchema`) only so conversations frozen on `archive-tools-v4`/`v5` keep validating; page mode ignores `max_chars`/`limit`, and a legacy `offset` selects the containing page. It slices a cached full document without calling the provider on a cache hit. Changing these arguments, the footer, or its semantics requires a `TOOLS_VERSION` bump.
- Every `web_search` `<result>` and every `<web_fetch>` carries a short `id` (`w1`, `w2`, …) that the model cites inline as `[web:wN]`. Numbers come from the private `agent_web_source` table: assigned in order of first appearance under a per-conversation advisory lock, reused when a URL returns, and listed by `GET /agent/conversations/{id}/web-sources` (`listAgentWebSources`). Tool `data` stores the same `ref`. Outside a conversation the numbers are local to one result. A numbering failure must never fail the web tool. Web ids are never archive citations; `CITATION_PATTERN` accepts them only so the UI and saved answers keep them.
- `web_search` always renders one trailing `<search_hint>` child with `truncated`, `excerpts_clipped`, `provider_truncated`, and `excerpt_limit`; every `<result>` also carries `content_chars`, `excerpt_chars`, and `excerpt_truncated` so clipping is local and visible. Search results are always bounded excerpts, so the hint is unconditional; removing it re-introduces silent truncation. The hint body is fixed English with no titles, URLs, or counts interpolated, and changing its attributes or body requires a `TOOLS_VERSION` bump.
- Fail closed on provider/tool errors. Use safe codes and bounded details; never expose raw provider bodies, keys, SQL, or stack traces to clients.
- Retry a transient provider failure (`5xx`, `429`, timeout, or network error) only while no text delta has reached the client. A retry after visible output would duplicate text, so leave that failure to the durable UI retry path. When a failure or timeout interrupts a stream after deltas, persist the visible prefix in the failed assistant entry (`data.partial`) so reloading the transcript keeps what the reader already saw; the failed entry stays excluded from future provider context.
- Provider and run logs are English `key=value` lines with stable correlation fields (`request_id`, `run_id`, `step`, `call_id`, `attempt`). Log counts, status codes, latency, token usage, and the provider's bounded error code/message; never log prompt content, tool arguments, API keys, or a raw response body.
- Enforce approval through the backend `approved` flag. Never let model arguments, route input, or UI state bypass the durable approval row.
- Treat runtime limits as data, not constants. Read them from the immutable snapshot; do not add hidden per-module caps that contradict `agent_config`.
- When changing API schemas or models, update the Alembic revision and regenerate the OpenAPI/Orval client together.
- Put integration coverage in `backend/tests/test_agent.py` or a focused companion module such as `test_agent_provider_retry.py`. Use `FakeChatGenerator` through `app.state.agent_chat_generator`; do not call a real provider.

uv run ruff check app/module/agent tests/test_agent.py
uv run mypy app
PYTHONUNBUFFERED=1 uv run pytest -q tests/test_agent.py tests/test_chat_attachments.py

Run the full suite when changing context replay, tool behavior, persistence, or SSE contracts. Do not test against a live archive database.
